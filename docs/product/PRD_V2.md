Product Requirements Document (PRD)
Product Name: IntelliAttend Smart Board Portal
Platform: Hybrid Application (Flutter for Android/Windows)
Document Version: 3.0 (Final Architecture)
Date: March 15, 2026

1. Product Vision & Objective
The IntelliAttend Smart Board Portal is an offline-resilient, automated attendance engine designed for university classrooms. It eliminates manual roll calls by utilizing a hyper-dynamic, cryptographically secure 2-minute QR sprint. The system enforces strict behavioral compliance: the Smart Board handles the automated "Happy Path" (on-time, has phone), while all edge cases (latecomers, dead/forgotten phones) are pushed to a high-friction manual ID-scan process on the Faculty's mobile device, keeping the classroom display pure and uninterrupted for teaching.

2. Target Audience
Primary Users: University Faculty and Teaching Assistants (TAs).

Secondary Users: Students (interacting via their separate mobile app).

Tertiary Users: Campus IT Administrators.

3. Core System Architecture: The "Offline-First" TOTP Paradigm
Unlike traditional systems that fail when Wi-Fi drops, IntelliAttend uses a Time-based One-Time Password (TOTP) architecture.

Upon login, the server shares a cryptographic session_secret (seed) with the Smart Board.

The board uses this seed to generate valid QR codes locally, requiring zero internet connection to function during the lecture.

If the board loses internet, students with mobile data (4G/5G) can still successfully mark attendance by scanning the blindly generated TOTP QR code.

4. Functional Requirements: The Smart Board Portal
4.1. Secure Handshake & Time-Sync
Biometric OTP Entry: The default idle screen displays a locked numeric keypad. Faculty must enter a 6-digit OTP generated by their authenticated personal mobile app.

NTP Time Correction: Upon OTP validation, the board must ping an NTP (Network Time Protocol) server to calculate its clock_skew (the exact millisecond difference between the board's hardware clock and the backend server). This ensures the TOTP algorithm never drifts.

State Persistence (Crash Recovery): The board must instantly write the active Session_ID and session_secret to an encrypted local Isar Database. If the board loses power mid-lecture, it must automatically bypass the OTP screen upon reboot and resume the active session without data loss.

4.2. The 2-Minute QR Sprint (Automated Happy Path)
Start Trigger: The faculty taps a prominent "Start Attendance" button on the UI.

The Timer: A massive 02:00 countdown timer appears on screen.

The TOTP Engine: A background Dart Isolate generates a new SHA-256 hashed QR code every 3 to 4 seconds, utilizing the session_secret and corrected NTP time.

Live Dashboard: As the server validates student scans, a WebSocket connection pushes targeted updates to the board, instantly turning individual student UI tiles from white to green.

Auto-Shutdown: At exactly 00:00, the QR engine terminates. The server permanently locks the primary attendance endpoint for that session.

4.3. Offline Resilience (The Isar Vault)
Local Queuing: If the campus Wi-Fi drops completely, the board must capture incoming student scans via local Bluetooth/LAN connections and queue them in the encrypted Isar Vault.

Background Sync: Upon detecting Wi-Fi restoration, a background Sync Manager must push all queued offline scans to the server and subsequently wipe the local cache.

4.4. Presentation Mode Transition
UI Shift: Once the 2-minute attendance window closes, the QR code UI must vanish. The screen transitions into Presentation Mode, prioritizing the faculty's teaching materials (downloaded PDFs/PPTs via cloud sync).

Minimized Dashboard: The full attendance grid minimizes to a small, unobtrusive summary widget (e.g., "Present: 55/60") in the corner of the screen.

4.5. Session Termination (Punch-Out)
Action: The faculty taps "End Session."

Teardown: The system logs the departure time for HR tracking, drops the WebSocket connection, wipes all downloaded presentation files from the local cache, and returns to the locked Kiosk screen.

5. Functional Requirements: The Manual Exception Protocol (Faculty App)
The Smart Board strictly prohibits manual attendance entry. All exceptions are handled via the Faculty/TA Mobile App.

The Scope: Latecomers, dead student phones, and forgotten student phones.

The Workflow (Post-Class Line): Students requiring exceptions must wait until the automated 2-minute window is over (or until class ends).

Physical ID Scanning: The Faculty or assigned TA opens their mobile app to the "ID Scanner" module. They use the phone's camera to scan the barcode/RFID on the student's physical university ID card.

Biometric Authorization: Before the manual override is sent to the server, the Faculty/TA must authorize the action using their device's native biometric scanner (Fingerprint/FaceID).

Tardy Flagging: The system allows the Faculty to categorize the manual scan as "Present" (for a dead phone) or "Tardy" (for arriving late).

6. Technical & Security Constraints
Validation Window (Sliding Scale): To combat slight hardware time-drift, the backend server must accept the current 3-second TOTP token, as well as the immediate previous and next tokens (a ~9-second sliding grace period).

Hardware Keystore: The session_secret seed must be stored securely using the Smart Board OS's hardware-backed Keystore, preventing extraction via malicious USB payloads.

Wake Lock: The application must utilize an OS-level wake lock to prevent the screen from dimming or sleeping during an active session.

7. Explicitly Out of Scope
Manual 6-digit corner codes on the smart board.

Any manual attendance override buttons on the smart board UI.

Continuous QR generation lasting the entire lecture duration.
