# Implementation Plan: Stale Credentials Survive Uninstall/Reinstall

## Problem Statement

When a user uninstalls IntelliAttend SmartBoard and reinstalls it, the previous login credentials and device registration persist. This means:

1. The app launches directly into the main screen without asking for Board ID/Password
2. If incorrect credentials were entered before uninstall, they remain incorrect **forever** — there is no way to recover without the hidden reset mechanism
3. The user is locked out with no visible way to re-register

## Root Cause Analysis

### Data Persistence Layers

| Layer | Storage Mechanism | Location | Survives Uninstall? |
|-------|------------------|----------|-------------------|
| Auth tokens & board credentials | Windows Credential Manager (via `flutter_secure_storage`) | OS-managed | **YES** |
| Device registration, timetable, sessions | Isar database (via `path_provider`) | `%APPDATA%\IntelliAttend\SmartBoard\` | **YES** |
| Installation state / context | JSON files on disk | `%LOCALAPPDATA%\IntelliAttendSmartBoard\Data\` | **YES** (MSI preserves `Data\`) |
| Application binaries | MSI-managed files | `%LOCALAPPDATA%\IntelliAttendSmartBoard\App\` | **NO** (deleted on uninstall) |

### MSI Installer Contract (from `product.wxs`)

> **G-5**: Clean uninstall removes `App\`, **preserves** `Data\Config\Backup\Logs\`

The MSI intentionally preserves user data directories. Combined with Windows Credential Manager and `%APPDATA%` being outside the MSI's scope, **all authentication state survives uninstall**.

### Boot Flow

```
BootScreen._performHandshake()
  └─ deviceRepository.getRegistration()  ← reads Isar DeviceRegistration
       ├─ null → RegistrationScreen (login page)
       └─ exists → SessionOrchestratorScreen (skips login entirely)
```

## Scenarios

### Scenario A: Clean First Install
1. User installs the app for the first time
2. No `DeviceRegistration` in Isar → RegistrationScreen shown
3. User enters credentials, registers successfully
4. Data saved to SecureStorage + Isar
5. ✅ **Correct behavior**

### Scenario B: Normal Restart / Reboot
1. User restarts the app normally on same install
2. Marker file (`.initialized`) exists in `App\`
3. `clearStaleDataIfReinstall()` returns early — no action
4. Isar has valid `DeviceRegistration` → goes to main screen
5. ✅ **Correct behavior**

### Scenario C: Uninstall + Reinstall (Current Bug)
1. User enters **incorrect** SmartBoard ID/Password
2. App stores wrong credentials + registers with wrong data
3. User uninstalls the app
4. User reinstalls the app
5. Isar still has `DeviceRegistration`, SecureStorage still has tokens
6. BootScreen finds old registration → skips to main screen
7. ❌ **User is locked out with incorrect credentials forever**

### Scenario D: Uninstall + Reinstall (After Fix)
1. User enters **incorrect** SmartBoard ID/Password
2. App stores wrong credentials + registers with wrong data
3. User uninstalls the app → `App\` directory deleted, marker file gone
4. User reinstalls the app
5. `clearStaleDataIfReinstall()` runs:
   - Marker file missing → checks for stale data
   - Finds old `DeviceRegistration` + credentials → clears everything
6. BootScreen finds no registration → shows RegistrationScreen
7. ✅ **User can enter correct credentials**

### Scenario E: Normal Update (MajorUpgrade)
1. User has working app with correct credentials
2. MSI upgrade runs — files replaced in-place, `App\` NOT deleted
3. Marker file survives (still exists in updated `App\`)
4. `clearStaleDataIfReinstall()` returns early
5. Normal boot continues with existing data
6. ✅ **No disruption**

### Scenario F: Hidden Reset Button (45s Hold)
1. User is on IdleScreen or BootScreen
2. User long-presses the logo for 45 seconds
3. System wipe triggered → SecureStorage cleared, Isar cleared
4. App navigates to RegistrationScreen
5. ✅ **User can re-register with correct credentials**

### Scenario G: Bug — Accidental Wipe (Edge Case)
*Could the fix accidentally wipe data on a normal update?*
- **No** — marker file is in `App\` which survives in-place upgrades
- The marker is only missing when `App\` is deleted (uninstall) or never existed (first install)
- ✅ **Safe**

## Proposed Solution

### Core Fix: Reinstall Detection via Marker File

Add a marker file (`.initialized`) to the `App\` directory. Since MSI deletes `App\` on uninstall, the marker disappears on uninstall and is absent on reinstall.

**Implementation points:**

| Step | File | What |
|------|------|------|
| 1 | `lib/core/lifecycle/lifecycle_phases.dart` | Add `clearStaleDataIfReinstall()` method |
| 2 | `lib/core/lifecycle/app_lifecycle_manager.dart` | Call it in DATABASE phase after Isar init |

**Algorithm:**
```
if marker file exists:
    return (normal startup)

if boardEmail or refreshToken or DeviceRegistration exists:
    SecureStorageService.clearAll()
    Isar: clear all collections (deviceRegistrations, timetableEntrys,
          activeSessions, completedSessions, hydrationProfiles,
          hydrationRosters, storedNotifications)

create marker file at %LOCALAPPDATA%\IntelliAttendSmartBoard\App\.initialized
```

### Existing Reset Mechanism Integration

The existing **Boot Screen Logo Long-Press** (`boot_screen.dart:122`) already provides a hidden admin reset:
- Long-press logo → 6-digit admin PIN prompt → server deregistration → local wipe → fresh registration screen
- Current hold duration: ~500ms (Flutter default), **not 45 seconds**

Two options:
- **Option A**: Keep the 45s hold as a separate, even-harder-to-trigger reset on the IdleScreen (more discoverable than a PIN)
- **Option B**: Document the existing boot-screen logo long-press as the official "hidden reset" and use the reinstall fix as the primary recovery path

**Recommendation**: Implement both — the reinstall fix handles the uninstall/reinstall scenario automatically, and the existing boot-screen long-press+ PIN handles cases where the user is still on the same install but needs to re-register.

# Update Loop Fix: Dismiss + Circuit Breaker + Settings Button

## Problem Statement

When the auto-update mechanism fails (download error, hash mismatch, agent launch failure), the application gets stuck in an infinite retry loop:

1. Heartbeat/WebSocket delivers an `UpdateManifest`
2. `AutoUpdater.checkForUpdate()` starts downloading → fails → sets `UpdateState.failed`
3. Next heartbeat delivers the same manifest → dedup fingerprint was reset by the exception → retries → fails again
4. **No way out**: the UpdateOverlay only shows a Dismiss button in the `failed` state. If the download hangs mid-stream (e.g., server stall), there is no dismiss at all — the user is completely locked out.

## Root Cause Analysis

| Issue | File | Detail |
|-------|------|--------|
| No dismiss during active states | `update_overlay.dart:83-85` | `_buildErrorFooter` (Dismiss button) is only rendered when `state == UpdateState.failed`. During `downloading`, `verifying`, `installing` — no dismiss exists. |
| Failed state doesn't block retry | `auto_updater.dart:243` | Guard condition `progress.value!.state != UpdateState.failed` means failed states fall through and re-trigger immediately. |
| Exception resets dedup fingerprint | `auto_updater.dart:298` | `_lastCheckedManifestFingerprint = null` on exception allows the exact same manifest to re-trigger on next delivery. |
| No max-failure circuit breaker | — | Consecutive failures accumulate infinitely with no back-off or stop. |
| No user-facing "update available" in settings | — | Users have no way to see or manually trigger/retry an update from the UI. |

## Solution Design

### A. Dismiss at All States (`auto_updater.dart` + `update_overlay.dart`)

A Dismiss/Cancel button is added to the overlay for EVERY non-idle state. When pressed:

- **During `downloading`**: abort the in-progress HTTP stream by closing the `http.Client`, delete the partial MSI file, clear progress to `null`.
- **During `verifying` / `installing`**: clear progress to `null` (no active network to cancel).
- **During `failed`**: clear progress to `null` (existing behavior, now unified).

The dismiss also resets `_lastCheckedManifestFingerprint` so the next heartbeat re-evaluates (rather than being permanently blocked). However, the **circuit breaker** prevents immediate re-trigger loops.

### B. Circuit Breaker (`auto_updater.dart`)

Track consecutive failures per version fingerprint. After **3 consecutive failures** for the same version, open the circuit:

- `checkForUpdate()` returns early with a log message and does NOT start a new download.
- The `availableUpdate` notifier remains set so the Settings screen can show the button.
- The circuit resets when:
  - A **WebSocket `update_available` push** arrives (admin re-push = explicit intent).
  - The user clicks **"Retry Update"** in Settings.
  - A **different version** appears in a new manifest.
  - The app restarts (counter is in-memory).

### C. `availableUpdate` Notifier (`auto_updater.dart`)

A new `ValueNotifier<UpdateManifest?>` named `availableUpdate` is set whenever `checkForUpdate` determines a newer version exists but does not immediately start (circuit open, user dismissed, etc.). It is cleared when:
- The update completes successfully.
- The user dismisses.

### D. Fix `checkForUpdate` Guard (`auto_updater.dart`)

Rewrite the in-progress guard (line 242-252) to:
- Block retry when `state == UpdateState.failed` unless `force == true`.
- Block retry when circuit breaker is tripped.
- Still allow force-update to override a stuck/long-running attempt (>5 min).

### E. Settings "Update Available" Button (`settings_screen.dart`)

Add a new section "UPDATE" in the Settings screen after "SYSTEM ACTIONS". When `AutoUpdater.availableUpdate.value` is non-null, show a styled action button:

- **Label**: "UPDATE AVAILABLE — v{version}" (when idle / dismissed)
- **Label**: "DOWNLOADING... XX%" or "VERIFYING..." / "INSTALLING..." (during progress)
- **Label**: "RETRY UPDATE" (when failed)
- **Icon**: `Icons.system_update_alt_rounded`
- **Color**: teal (matching `_buildActionButton` style)
- **On Tap**: triggers `AutoUpdater.checkForUpdate()` or `AutoUpdater.resetCircuitBreaker()` plus retry

# Self-Update Failure Fix: Dynamic InstallPaths + Launch-Failure Circuit Breaker + CI Code Signing

## Problem Statement

Boards stuck on an older version report **"Failed to launch update agent. Try again later."** every heartbeat:

1. Manifest says a newer version exists → the app downloads and SHA-256-verifies the installer
2. `UpdateAgentLauncher.launch()` cannot find `update_agent.exe` because `InstallPaths` hardcodes the `App\` directory
3. Since v5.5.0.12 the Inno Setup installer writes binaries to `%LOCALAPPDATA%\IntelliAttendSmartBoard\` **root**, not `App\`
4. Launch returns `false` → `AutoUpdater` shows the failure error
5. Because the launch failure was swallowed (no exception), the circuit breaker never tripped → **retried on every heartbeat forever**, hammering the server with repeated downloads

## Root Cause Analysis

| Issue | File | Detail |
|-------|------|--------|
| Hardcoded `App\` binary path | `lib/core/config/install_paths.dart` | `appDir` returned `$root\App`, but the Inno installer (since v5.5.0.12) installs to `$root` — `update_agent.exe` never found |
| Split-brain layout | `lib/services/update_health_monitor.dart` | Already used `Platform.resolvedExecutable` (root layout) while `InstallPaths` used `App\` — two different notions of "app dir" |
| Swallowed launch failure | `lib/services/auto_updater.dart` | `launch()` returning `false` set `UpdateState.failed` but did **not** throw → `_incrementCircuitBreaker` never ran → infinite heartbeat retries |
| Strict Authenticode enforcement | `windows/update_agent/main.cpp:132-138`, `289-294` | Agent rejects unsigned installers AND unsigned installed exes |
| Legacy CI signing | `.github/workflows/auto-deploy.yml:366-381` | Only `setup.exe` signed, via `Set-AuthenticodeSignature` + legacy `/t`-style RFC3161 timestamping; app exe + `update_agent.exe` shipped unsigned → agent would reject the update on every board |
| Checksum key-order mismatch | `windows/update_agent/checksum.cpp` | `VerifyChecksum` rebuilt the payload by iterating a `std::map` → **alphabetically sorted** keys, but the app's checksum (and the agent's own `WriteUpdateState`) use **insertion order** (`schema, owner, installer_path, …`). Every app→agent handoff would fail `ValidateStateFile` even with a found+signed agent |

**Live-machine confirmation:** this dev machine runs v5.5.0+15 installed to root with an empty `App\` directory; the autostart registry key points at the root exe.

## Solution Design

### A. Dynamic `InstallPaths` (`lib/core/config/install_paths.dart`)

Resolve binary paths from the running executable instead of assuming a fixed layout:

- `root` honors `testRootOverride` (kept, now `@visibleForTesting`)
- `appDir` → `File(Platform.resolvedExecutable).parent.path` on Windows (root layout); falls back to `$root\App` only if resolution fails
- `exePath` → `Platform.resolvedExecutable`
- `updateAgentPath` → `$appDir\update_agent.exe` (co-located with the exe, matching the installer layout)

This works for both MSI (`App\`) and Inno Setup (root) installs with **no installer change**.

### B. Retry-Loop Hardening (`lib/services/auto_updater.dart`)

When `launch()` returns `false`, `throw` after setting the failure state so `_startUpdate`'s error path increments the circuit breaker. Persistent launch failures (e.g. missing `update_agent.exe`) now open the circuit after 3 attempts instead of retrying forever.

### C. Professional CI Signing (`auto-deploy.yml`)

- **New step** "Sign application binaries (required for self-update)": signs app exe + `update_agent.exe` **before** Inno packaging so signed binaries ship inside `setup.exe` — required by the C++ agent's Authenticode checks
- **Upgraded** installer signing to `signtool` with RFC 3161 `/tr` + `/td sha256` (durable timestamps)
- **New step** "Verify Authenticode signatures": `Get-AuthenticodeSignature` must be `Valid` on `setup.exe`, the app exe, and `update_agent.exe` — release fails otherwise

### D. CI Must Build `update_agent.exe` (`auto-deploy.yml`)

**Blocker found during end-to-end audit:** `flutter build windows` does **not** compile the C++ agent, and the workflow had no step that does. On a fresh `windows-latest` runner the "Copy update_agent.exe to bundle" step found nothing → the release could never be produced.

- **New step** "Build update_agent.exe": `cmake -S windows\update_agent -B build\windows\x64\update_agent -G "Visual Studio 17 2022" -A x64` + `cmake --build --config Release`, fail-fast
- `setup.iss` uses `Source: "{SourceDir}\*"` with `recursesubdirs` → the built agent is bundled automatically
- Sign/verify steps now use the detected `app_name` instead of a hardcoded exe name

### E. Signing Secrets Now Required (`auto-deploy.yml`)

The agent **hard-rejects** unsigned installers and unsigned app binaries (`main.cpp:132-138`, `289-294`). An unsigned release would fail self-update on every board. `SIGN_CERT_BASE64` + `SIGN_PASSWORD` are now part of the required-secrets validation → the build fails fast with a clear message instead of shipping a release boards reject.

### F. Checksum Canonical-Order Fix (`windows/update_agent/checksum.cpp`)

`VerifyChecksum` rebuilt the JSON payload by iterating `std::map<std::wstring,…>` (keys **sorted alphabetically**), but the app computes its checksum — and the agent's `WriteUpdateState` writes — in **insertion order**. The payloads differed, so the app→agent handoff always failed validation. Fix: `VerifyChecksum` now rebuilds the payload in an explicit canonical key order identical to `WriteUpdateState` (`schema, owner, installer_path, target_version, expected_sha256, app_pid, app_exe_path, log_path, state, error, created_at, completed_at, attempt`), skipping absent keys. The agent also honors the `owner` field the app doesn't write.

**Proven locally:** fake signed `setup.exe` (1.2 MB) + fake signed app (v5.5.0.16) → Dart-format state file → agent run → checksum valid, install, version+Authenticode verify, relaunch, exit 0. Before the fix the same state file exited `InvalidState` (5).
